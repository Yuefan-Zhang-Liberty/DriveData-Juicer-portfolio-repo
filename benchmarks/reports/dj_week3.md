Generated by `data_juicer/run_benchmark.py`, driving the real `dj-process` CLI against `data_juicer/process_local.yaml` at three run-scale tiers. Each tier's manifest is a deterministic slice of the sliding-window clip plan produced by `export_gold_manifest.py` (see that script's docstring for the overlap caveat: nuScenes mini has only 10 scenes, so the 500-clip tier is reached via overlapping windows over each scene's CAM_FRONT frame sequence, not 500 independent recordings).

## One-command deliverable

The literal completion-gate command runs standalone (no CLI overrides -- uses the
`process_local.yaml` defaults, which point at the 500-clip manifest):

```
MP_START_METHOD=fork dj-process --config data_juicer/process_local.yaml
```

Confirmed to exit 0 and export `data_juicer/outputs/phase3/result.jsonl` with the same
per-op retention as the 500-tier row above.

## Environment bugs found and fixed this phase

Three independent, unrelated bugs had to be resolved before any real (non-zero) output
came out of the pipeline:

1. **Manifest path convention.** `export_gold_manifest.py` originally wrote each clip's
   `videos` path relative to the project root. Data-Juicer actually resolves relative
   video paths against `dirname(dataset_path)` -- the manifest file's own directory
   (`data-juicer/data_juicer/format/formatter.py`) -- so every single sample (not just the
   deliberately corrupted one) was silently dropped as unresolvable on the very first op.
   Fixed by computing `videos` paths relative to `--manifest-dir` instead.
2. **`av` version pin.** An earlier, unpinned `pip install av` had installed `17.1.0`, but
   Data-Juicer's own `pyproject.toml` pins `av==13.1.0`; the newer release removed/changed
   the `VideoCodecContext.close()` API that `mm_utils.py`'s `close_video()` depends on,
   crashing every real sample in `video_aspect_ratio_filter` with
   `AttributeError: 'av.video.codeccontext.VideoCodecContext' object has no attribute 'close'`.
   Fixed by reinstalling the pinned version: `uv pip install "av==13.1.0"`.
3. **`MP_START_METHOD=fork` required on this host.** `video_motion_score_filter` is
   registered in Data-Juicer's `UNFORKABLE` set (it uses OpenCV), which forces the
   multiprocessing start method to `forkserver`/`spawn` instead of `fork`. Both are broken
   on this specific shared, multi-user, 224-core server -- they reliably crashed with
   `multiprocessing.context.AuthenticationError: digest sent was rejected` (most likely
   contention with other users' concurrent multiprocessing jobs on the same host, though
   not conclusively proven), while plain `fork` worked reliably for every op across every
   run. Rather than work around this outside the framework, patched the vendored
   `data-juicer/` fork's `setup_mp()` (`data_juicer/utils/process_utils.py`) so an explicit
   `MP_START_METHOD` env var always wins, even when Data-Juicer itself passed a restricted
   candidate list for an unforkable op. The patch is opt-in: default behavior for anyone
   who doesn't set the env var is unchanged. All commands in this report were run with
   `MP_START_METHOD=fork` set.
